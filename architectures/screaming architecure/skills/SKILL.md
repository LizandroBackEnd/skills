# CORE PHILOSOPHY AND ARCHITECTURAL FOUNDATIONS

## The Core Maxim of Screaming Architecture
Software architectures must scream their domain intent, business purpose, and use-case capabilities rather than the underlying delivery mechanism or technical framework. When an engineer opens the top-level directory structure of a repository, the architecture must immediately communicate domain contexts such as Healthcare System, Order Management, or Payment Processing - not Framework structures like Rails, Express, NestJS, or React.
1. Frameworks as Tools, Not Architectures: Frameworks are external delivery tools and should remain decoupled from business rules. Conforming an architecture to a framework's folder structure binds business logic to external dependencies, hindering testability and long-term refactoring.
2. Use-Case Centricity: Software structures exist primarily to support the use-cases of the application. Deferring technical decisions regarding databases, web servers, and UI frameworks allows the core domain logic to stabilize independently of environmental changes.

## Package by Feature vs. Package by Technical Layer
Structuring codebases by technical layer (such as flat top-level folders for `/controllers`, `/services`, `/models`, `/views`, or `/components`) obscures the domain boundaries of an application. 
1. Technical Layering Pitfalls: In a package-by-layer structure, modifying a single business use-case requires navigating across multiple disparate directories, increasing cognitive load and forcing developers to mentally stitch together scattered domain files.
2. Package-by-Feature Benefits: Grouping files by business feature (e.g., `src/features/orders/`, `src/features/billing/`) isolates related domain logic, interfaces, state management, and UI components into cohesive, self-contained modules. This modularity enhances team collaboration, supports clean deletion of legacy features, and accelerates onboarding.

## The Dependency Rule and Inward Flow
Clean Architecture enforces strict boundary isolation through the Dependency Rule.
1. Inward Dependency Flow: Source code dependencies must point strictly inward toward higher-level policies and core business logic. Inner circles encapsulating Entities and Use Cases must remain entirely unaware of outer circles such as Databases, REST Controllers, Web UIs, or Third-Party SDKs.
2. Decoupled Business Logic: Core business rules must not import data formats, ORM model instances, or framework-specific objects generated by outer layers. Input parameters and return values crossing layer boundaries must use primitive types or plain Data Transfer Objects (DTOs).

# DOMAIN BOUNDARIES AND ENCAPSULATION RULES

## Bounded Context Translation to Feature Modules
In Domain-Driven Design (DDD), a Bounded Context defines explicit boundary limits within which a specific domain model remains internally consistent and unified.
1. Subdomain Isolation: Each distinct Bounded Context translates directly to a top-level feature module directory (e.g., `src/features/<feature-name>/`). Polysemic domain concepts (such as a `Customer` or `Product`) that have different meanings across context boundaries must maintain independent model definitions inside their respective feature folders rather than sharing a single bloated global model.
2. Tactical Encapsulation: Within a feature directory, tactical domain elements - including entities, value objects, domain services, use-cases, UI components, state stores, and data-access adapters - are co-located exclusively for that context.

## Public API Encapsulation via Barrel Index Files
To preserve structural encapsulation and prevent leakages of internal implementation details, every feature directory must establish an explicit public contract.
1. Barrel File Boundary (`index.ts`): A feature directory exposes its public API strictly through a top-level `index.ts` barrel file. Only components, hooks, actions, types, and services intended for consumption outside the feature may be re-exported from this file.
2. Private Internal Structure: Sub-directories within a feature (such as `components/`, `api/`, `utils/`, `use-cases/`, or `stores/`) remain private to the feature module. External modules are prohibited from directly reaching inside private sub-directories.

## Cross-Feature Communication Rules
1. Unidirectional Layer Flow: The architecture enforces a strict unidirectional dependency flow: shared core primitives flow into feature modules, and feature modules are composed at the application layer (`shared -> features -> app`).
2. Inter-Feature Isolation: Direct imports across independent feature directories are prohibited. Features must remain completely decoupled from one another; orchestration across multiple features occurs exclusively at the top-level application or routing layer.
3. Illegal Deep Imports: Importing directly from another feature's private internal files (e.g., `import { helper } from '@/features/auth/utils/helper'`) violates encapsulation boundaries and must be blocked by linting engines.

# STEP-BY-STEP WORKFLOW: STRUCTURING A NEW DOMAIN FEATURE

When architecting a new business capability or refactoring legacy monolithic code, follow this sequential 5-step algorithm:

## Step 1: Context Identification and Bounded Modeling
Identify the business domain capability and determine whether it belongs within an existing Bounded Context or requires a new feature module. Define the Ubiquitous Language terms and domain boundary limits before creating any code files.

## Step 2: Feature Directory Scaffolding
Create the dedicated feature directory under `src/features/<feature-name>/`. Scaffold only the specific sub-directories required for the feature's immediate responsibility:
- `api/`: API request declarations, endpoints, or query hooks.
- `components/`: UI display elements scoped strictly to this feature.
- `hooks/` or `stores/`: State management and reactive handlers.
- `use-cases/` or `services/`: Application-specific business logic orchestration.
- `types/`: Domain interfaces, DTOs, and type definitions.

## Step 3: Core Domain and Use-Case Implementation
Implement the core business entities, value objects, and use-cases inside the feature module. Ensure zero external dependencies on web frameworks, ORMs, or UI elements within the core domain rules.

## Step 4: Infrastructure Adapter and UI Integration
Build the presentation components, data-fetching hooks, or database repository adapters that connect external frameworks to the inner use-cases. Verify that data crossing layer boundaries is mapped into plain structures.

## Step 5: Public API Export and Boundary Validation
Expose the public interface of the feature by exporting selected components, types, and hooks inside `src/features/<feature-name>/index.ts`. Run static analysis linters to confirm no private internal paths are imported externally.

# ADVANCED PATTERNS AND CONCRETE STRUCTURES

## a) Full-Stack / Backend Domain Architecture
A clean backend feature module encapsulates domain entities, use-cases, repository interfaces, and delivery adapters (HTTP controllers, event consumers) within a single folder.

### INCORRECT / FRAMEWORK-CENTRIC
Top-level technical folders fragment domain logic across the repository, making it impossible to ascertain business capabilities from folder structures.
```
src/
+-- controllers/
|   +-- orderController.ts
|   +-- userController.ts
+-- services/
|   +-- orderService.ts
|   +-- userService.ts
+-- models/
|   +-- orderModel.ts
|   +-- userModel.ts
+-- repositories/
    +-- orderRepository.ts
```

### CORRECT / DOMAIN-SCREAMING
The directory structure screams the business domain (`orders`), isolating business logic, use-cases, and interfaces from delivery frameworks.
```
src/
+-- features/
    +-- orders/
        +-- index.ts                   # Public API barrel export
        +-- domain/
        |   +-- orderEntity.ts         # Core domain entity & business rules
        |   +-- orderId.ts             # Value object for typed ID
        |   +-- orderRepository.ts     # Abstract repository interface
        +-- use-cases/
        |   +-- createOrder.ts         # Application use-case handler
        |   +-- cancelOrder.ts         # Application use-case handler
        +-- adapters/
        |   +-- http/
        |   |   +-- orderController.ts # Express / NestJS delivery controller
        |   +-- persistence/
        |       +-- prismaOrderRepo.ts # Database adapter implementing orderRepository
        +-- dtos/
            +-- createOrderDto.ts      # Plain request/response DTOs
```

## b) Modern Frontend Architecture (Bulletproof React / Next.js / Astro)
A frontend feature module encapsulates UI components, state stores, data-fetching actions, and type definitions.

### INCORRECT / FRAMEWORK-CENTRIC
Grouping by framework mechanics causes widespread cross-file dependencies and leaking implementation details.
```
src/
+-- components/
|   +-- OrderList.tsx
|   +-- OrderItem.tsx
|   +-- UserAvatar.tsx
+-- hooks/
|   +-- useOrders.ts
+-- api/
|   +-- orderApi.ts
+-- types/
    +-- orderTypes.ts
```

### CORRECT / DOMAIN-SCREAMING
Encapsulates UI rendering, data hooks, and Zod schema validations inside a cohesive feature module.
```
src/
+-- features/
    +-- order-checkout/
        +-- index.ts                   # Public API exporting OrderCheckout component & public types
        +-- api/
        |   +-- getOrderDetails.ts     # API request fetching logic
        |   +-- submitCheckout.ts      # Mutation request handler
        +-- components/
        |   +-- OrderSummary.tsx       # Private feature UI component
        |   +-- PaymentForm.tsx        # Private feature UI component
        +-- hooks/
        |   +-- useCheckoutFlow.ts     # Feature state machine & reactive hooks
        +-- schemas/
        |   +-- checkoutSchema.ts      # Zod validation schema for form inputs
        +-- types/
            +-- checkoutTypes.ts       # Internal type interfaces
```

## c) Shared Code vs. Feature Code Rules
To prevent feature directories from becoming polluted or creating circular dependencies, strict allocation rules govern shared utilities.

```
src/
+-- app/                               # Global routing, providers, and layout composition
+-- assets/                            # Global static assets (images, fonts, global CSS)
+-- components/                        # Shared, domain-agnostic UI primitives (Button, Modal, Input)
+-- config/                            # Environment configuration and global constants
+-- hooks/                             # Shared React/framework hooks (useWindowSize, useTheme)
+-- lib/                               # Reusable preconfigured third-party clients (axios, prisma)
+-- stores/                            # Global application state stores (session, theme)
+-- types/                             # Global shared TypeScript interfaces
+-- utils/                             # Pure, stateless utility functions (formatDate, truncateString)
+-- features/                          # Isolated business domain modules
    +-- auth/
    +-- billing/
    +-- orders/
```
1. Feature-Specific Logic: Any component, helper, hook, or type that serves a single business capability must remain inside that feature's directory.
2. Shared Candidates: Code moves to top-level `src/components/`, `src/utils/`, or `src/lib/` strictly when it is completely domain-agnostic and required by two or more independent features.

# ANTI-PATTERNS AND PREVENTION CHECKLIST

Avoid these common architectural anti-patterns:

## 1. The "Common" or "Utils" Dumping Ground
* Anti-pattern: Creating catch-all directories like `src/common/` or generic `src/utils/` where business logic, UI helpers, and data mappers are indiscriminately dumped. This creates high coupling and turns shared folders into unmaintainable god-modules.
* Corrective action: Co-locate utilities and helpers directly within the specific feature module they serve. Reserve top-level `src/utils/` exclusively for pure, stateless functions (e.g., date formatting).

## 2. Circular Feature Dependencies
* Anti-pattern: Feature A importing from Feature B while Feature B imports from Feature A. This tightly couples bounded contexts, breaks build optimization, and violates domain boundaries.
* Corrective action: Elevate shared interactions to the application/routing layer (`src/app/`), or extract common domain concepts into a shared domain kernel.

## 3. Leaking Database Models Across Boundaries
* Anti-pattern: Passing ORM entity models or raw database row structures directly out of feature modules to external consumers or UI templates.
* Corrective action: Map internal database models to plain DTOs or primitive value structures before returning data across boundary interfaces.

## 4. Deep Internal Imports
* Anti-pattern: Reaching into private internal directories of another feature (e.g., `import { PaymentCard } from '@/features/billing/components/PaymentCard'`).
* Corrective action: Restrict external access strictly to the feature's `index.ts` public exports.

# ESLINT AND LINTER ENFORCEMENT CONFIGURATION

To mechanically enforce boundary restrictions, protect public barrel interfaces, and prevent illegal cross-feature imports, use `eslint-plugin-import` with `no-restricted-paths`.

```javascript
// .eslintrc.js
module.exports = {
  plugins: ['import'],
  rules: {
    'import/no-restricted-paths': [
      'error',
      {
        zones: [
          // 1. Prevent direct cross-feature imports (e.g., auth cannot import from orders)
          {
            target: './src/features/auth',
            from: './src/features',
            except: ['./auth'],
          },
          {
            target: './src/features/orders',
            from: './src/features',
            except: ['./orders'],
          },
          {
            target: './src/features/billing',
            from: './src/features',
            except: ['./billing'],
          },

          // 2. Enforce Unidirectional Architecture (features cannot import from app)
          {
            target: './src/features',
            from: './src/app',
          },

          // 3. Prevent shared infrastructure from importing from features or app
          {
            target: [
              './src/components',
              './src/hooks',
              './src/lib',
              './src/types',
              './src/utils',
            ],
            from: ['./src/features', './src/app'],
          },
        ],
      },
    ],
  },
};
```
